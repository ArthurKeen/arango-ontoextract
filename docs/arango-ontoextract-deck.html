Arango-OntoExtract

Living ontologies from documents and databases

Using LLMs to propose a formal model of a business — and building the machinery that makes a human's judgement about it survive.

Open source · MIT licence · Why "extract once" is the wrong mental model

Opening line: "Every company I've worked with has a model of its own business that exists nowhere in machine-readable form. It's in the decks, and it's implied by the database schema. This is a system that goes and gets it."

Set expectations: no prior knowledge of ontologies, OWL, or ArangoDB is assumed — everything gets defined as we go. About 20 minutes.

Part one

Knowledge you already own, in a form nothing can use

Two piles of latent structure, and why the obvious fix has never scaled.

Short act. Goal is to make the audience recognise their own organisation in the next two slides before any technology appears.

The problem

Two giant piles of latent structure

Pile one — documents

PDFs, decks, specs, wikis. These describe how the business actually thinks: its concepts, its taxonomies, its rules.

But it's prose. You can search it. You cannot reason over it.

Pile two — databases

Tables and columns that already encode a working model of the domain — but only physically.

A customers table and a places_order foreign key imply concepts. Nothing anywhere says "a Customer is a kind of Party," or "an Order must have at least one line item."

Both piles contain the same knowledge in different disguises. The document pile knows the meaning but not the structure; the database pile knows the structure but not the meaning.

Ask the room: how many of you could produce a single diagram that a machine could read, saying what your core business entities are and how they relate? Almost nobody can.

Definitions, once

An ontology is a schema that carries meaning

A machine-readable model of what exists in a domain and how it relates. Four ingredients:

Classes The things that exist Customer Order Loan Product
Properties What connects and describes them Order  —has→  Line Item
Hierarchy What is a kind of what Retail Mortgage  ⊂  Loan Product
Constraints What must be true Order  ≥1  Line Item

The standards for writing this down are called OWL and RDFS. That's the last acronym you need — software can traverse an ontology, validate against it, and reason over it.

Don't belabour OWL/RDFS. The one-sentence version people remember: "a database schema that carries meaning instead of just storage layout."

If someone asks how this differs from a data catalog: a catalog tells you what columns exist; an ontology tells you what they mean and lets a machine draw conclusions from it.

Why this isn't already solved

Hand-authored ontologies are expensive — and then they rot

  • Slow. Months of workshops to agree on what a "customer" is.
  • Expensive. Ontology engineering is a rare and costly skill.
  • Perishable. The documents and schemas it was derived from keep changing. The ontology doesn't.

The trap

Treat the ontology as a build artifact — produced once, signed off, filed — and it is wrong within a quarter and abandoned within a year.

This is the slide that explains why a genuinely useful idea from the 1990s never went mainstream. The cost was in human authoring, and there was no way to amortise it.

LLMs change the authoring cost. They do not, on their own, change the rot — that's the engineering problem the rest of the talk is about.

The thesis

The LLM proposes. The human disposes.

Arango-OntoExtract uses language models to propose an ontology — from documents and from live database schemas — then puts a domain expert in the loop to curate it.

Build artifact → Living knowledge graph
  • Grounded — every concept traces back to the slide or table it came from.
  • Versioned — nothing is overwritten; every change is reversible.
  • Revised — new evidence updates existing beliefs instead of triggering a re-extraction from scratch.
  • Self-repairing — deterministic fixes run before a human ever sees the result.

"Propose / dispose" is the phrase to repeat. Everything architectural in this system follows from taking it literally.

Flag the through-line early: the hard part isn't getting an LLM to emit an ontology. It's making the resulting artifact trustworthy enough to keep.

Part two

How it works

One database, a pipeline of agents, and a hard stop before anything is committed.

Shift into architecture. Warn the room this part has one piece of infrastructure vocabulary in it, and then it's over.

System at a glance

Three layers, one store

Workspace A single persistent stage — a graph canvas, an asset explorer, a timeline. Not a twelve-page wizard.
Backend Ingestion, extraction, entity resolution and curation services, orchestrated as a multi-agent state machine.
Database One engine holding the documents, the ontology graph, the vector embeddings and the search index.
Agent interface The whole platform is also exposed over MCP — the emerging standard for handing an application's capabilities to an AI agent as callable tools. A coding assistant can extract, query and curate without a human touching the UI.

Keep this brief — it's a map, not a destination. The only claim that matters is the third row, which the next slide justifies.

MCP question that always comes: yes, the agent path and the UI path hit the same services. There is no privileged back door.

The one piece of infrastructure vocabulary

Multi-model

ArangoDB does all four in one engine, one query language, one transaction. A single query can start at a document chunk, walk the ontology graph, filter by vector similarity and rank by text relevance — without leaving the database. The glue code between four systems is where the bugs live: a concept in the graph store whose embedding never reached the vector store; a document deleted here but not there.

This is the slide for the 99.9% who have never used ArangoDB. Don't sell the database — sell the absence of synchronisation. Provenance, retrieval and traversal are the same engine, so they cannot drift apart.

Vocabulary note if anyone reads the docs later: a "collection" is what everyone else calls a table, and a "named graph" is a declared bundle of them the engine will traverse as a unit.

Extraction

A pipeline of agents, not a prompt

"Send the document to an LLM and parse the JSON" fails in ways you cannot audit. Extraction here is a state machine with retries, a parallel fork, and a mandatory pause.

strategy→ extractor→ consistency→ quality judge ＋ entity resolution
→ belief revision→ structural gate→ subsumption judge→ filter→ human curation
  • Multi-pass with self-consistency. Keep only concepts that survive across passes — a cheap, effective hallucination filter.
  • Evidence-constrained. Every class and relationship carries the source chunks and quoted text that justify it.
  • A hard stop. Nothing reaches the curated ontology without a person — or an explicit written policy — saying yes.

Emphasise the fork: quality judging (an LLM-as-judge scoring faithfulness) and entity resolution (dedup via similarity + union-find clustering) run in parallel, then get reconciled.

The retry loop on the extractor fires when yield is suspiciously low — a document that produces two classes is usually a parsing failure, not a simple document.

Grounding

Every concept knows where it came from

  • Chunks keep their address. Document, page or slide number, section heading — preserved from the first byte.
  • Diagrams aren't silently dropped. Domain decks encode taxonomies in pictures. Every embedded image and scanned page is counted and represented, so omitted evidence is visible rather than invisible.
  • Click a class, see the slide. "Which document produced this, and which chunks contributed?" is a two-hop graph query, not a join across systems.

Why it matters

An ungrounded ontology is an opinion. A grounded one is a claim with a citation — and a curator can settle it in five seconds instead of relitigating it in a meeting.

The visual-evidence point lands well with anyone who has watched a text extractor silently skip the one slide that had the taxonomy on it.

Optional OCR/vision captioning appends clearly-labelled context the extractor can cite; it's off by default, and the counts are reported either way.

The other on-ramp

If you run a database, you already have a draft

Tables are already classes. Foreign keys are already relationships. Columns are already attributes. Nobody wrote it down as a formal model — but the model is there, and unlike an LLM's reading of a PDF, it is exactly right.

table / collection→class foreign key / edge→relationship
column→attribute unique index, check→constraint

No model in the loop

This path is deterministic — a mechanical walk of the live schema, with full provenance back to the source table. There is no LLM, and therefore nothing to hallucinate. Relational databases and ArangoDB are both first-class sources.

Good moment for the practical pitch: the fastest path to a first ontology is usually not documents. Point it at the production schema and you have a defensible draft in minutes.

Nice detail if there's time: the walk handles the "one Node table, one relations table" shape common in graph-database exports, where the real types hide in a field rather than in table names — it reads every distinct value and turns one physical table into the dozens of classes it actually encodes.

Don't start from zero

Eleven published vocabularies, one click, offline

Your own ontology shouldn't redefine what the world already standardised. The catalog imports established vocabularies as a foundation your work extends.

Schema.orgSOSA/SSNVSSo FIBO AgentsFIBO Accounting

Bundled, not fetched

Every entry ships inside the application. A first run works on a locked-down network, and can't be broken by someone else's server being down. Each keeps its tier — a published standard is never stamped as your own work.

Top row is foundational (core tier), bottom row domain. Both import through the same owl:imports machinery as anything else, so they're versioned and curatable like any other ontology.

War story worth telling if the room is technical: the importer originally read classes from rdf:type owl:Class only. Schema.org declares all ~1,000 of its types as rdfs:Class — an RDFS-era convention — so the entry advertising 800 classes imported zero. No error, no warning: an empty ontology and a green checkmark. Reading the union of both took it from 0 to 1,010 classes. Silent-success bugs are the expensive kind.

Part three

Making it trustworthy enough to keep

The engineering that separates a demo from a system anyone will still be using next year.

The heart of the talk. Everything here exists because automation without reversibility is unusable in an enterprise.

Temporal versioning

Nothing is overwritten. Ever.

  • Every node and edge carries a created and expired timestamp. "Current" just means expired is set to a far-future sentinel.
  • Editing a class doesn't destroy the old one — it expires that version and writes a new one.
  • Every read filters to "what was live at time T," where T defaults to now. History is queryable by construction, not by an audit log someone remembered to write.
  • The workspace exposes a VCR timeline: play forward, play backward, step, or drag to any past moment and watch the graph redraw as it stood that day.

Not a luxury feature

Time travel is the precondition for automating curation at all. If an agent-driven revision goes wrong, you can see exactly what changed, when, and by whom — and undo it.

Take that away and every autonomous behaviour in this system becomes unshippable.

Connect it forward: the autonomy dial at the end of the talk is only defensible because of this slide. Reversibility is what buys the right to automate.

Belief revision

The second document shouldn't start over

Adding a document shouldn't mean a fresh, disconnected extraction. Every class is a belief with evidence and a confidence score, and each comparison against the new source produces a verdict.

ReinforcedMore evidence agrees → raise confidenceautomatic
RefinedBetter definition supersedes the old versionautomatic
Gap-fillingGenuinely new concept → add itautomatic
ContradictedThe new source disagrees with the oldto a human
RetractThe belief no longer holds → expire itto a human

The mechanical majority is handled deterministically and cheaply — only contradictions reach a curator, and every revision is reversible.

The economics matter: paying an LLM to adjudicate every comparison is unaffordable and unnecessary. Spend tokens only where they change the answer.

Safety rails worth naming if asked: published items are protected, there's a circuit breaker on revision rate, and per-organisation budgets.

Self-repair

Fix the graph before it's a graph

LLM extractions fail in a characteristic way: dozens of plausible classes, but relationships pointing at targets that don't quite match anything, and classes connected to nothing at all. A disconnected schema.

Before the gate

island class connects to nothing

edge → dangling target

After — deterministic repairs only

URI normalization — re-point a target that matches a known class only by fragment.

Link recovery — when a target resolves to nothing, re-point it to the class named in the relationship's own evidence text.

The constraint that let us turn it on by default

Repairs rewrite relationship targets only — never a label, description, or evidence. So they cannot lower the faithfulness score. That's a guarantee held in place by a regression test, not a hope.

"No invention" is the phrase. The gate is allowed to reconnect things the source already supports; it is never allowed to add a fact.

If someone asks why not have the LLM fix it: because then the repair needs its own faithfulness audit, and you're back where you started.

Checked, not just generated

The one relation an LLM reaches for too often

Give a model one hierarchical relation and it uses it for everything. subClassOf means is a kind of — but any association the model senses gets flattened into it.

What the model writesWhat it actually meant
Tyre  subClassOf  Vehiclea tyre is part of a vehicle
Speed Rating  subClassOf  Tyrea speed rating is an attribute of a tyre
Manufacturer Instructions  subClassOf  Tyrea document describes a tyre

So a second judge tests every one

Each proposed edge is checked against the plain question "is every X a Y?", with a reason. It flags rather than deletes — a wrong subclass edge and a missing one are both defects — and it fails open: a judge that can block an extraction is worse than no judge.

Why it matters beyond tidiness: a reasoner walking a poisoned hierarchy will conclude a tyre inherits everything true of a vehicle. Bad subsumption doesn't just look wrong, it produces wrong answers downstream.

The judge's prompt carries a few-shot dictionary of real observed failures alongside genuine passes (Winter Tyre/Tyre, Unleaded Fuel/Fuel Type) — calibrated on measured behaviour, not an abstract instruction. The same dictionary went into the extraction prompt: not making the mistake beats catching it.

Roadmap, if asked: the real fix is an upper ontology giving the extractor partOf (transitive), hasAttribute and documentedBy to reach for, so associations stop being forced through the one relation available. Today the judge reports; that layer removes the cause. Specified in the PRD, not yet built.

An optional canvas view

See the structure most graph tools never draw

OWL lets you state a relationship two ways. As a plain property with a domain and a range — or as an axiom on the class itself. Published vocabularies lean heavily on the second form.

ssn:Deployment  rdfs:subClassOf
    [ owl:onProperty     ssn:deployedSystem ;
      owl:allValuesFrom  ssn:System ]

That says Deployment → deployedSystem → System as plainly as a property would. Most viewers only draw properties, so relations like this stay invisible and the classes look unconnected. AOE can draw them — as a view you switch on.

restrictions off ↔ restrictions on a display setting — never re-runs the layout

Lead with what it lets you do: audit what an imported vocabulary actually says. W3C's SOSA/SSN states most of its structure in restrictions — turn the view on and its real shape appears; leave it off and you see the plain property graph.

Why it's optional rather than always-on: restrictions add a lot of edges. You want them when you're inspecting a standard you've imported or checking whether a class is genuinely isolated; you want them out of the way when you're curating your own classes. That's a lens, the same pattern as colour-by-confidence.

The information was always in the database — imported correctly, stored as constraints. This view is what makes it legible. Toggling is a reducer decision on the graph already in memory, so it's instant in both directions.

From constraints to validation

OWL is open-world. SHACL is not.

Those same restrictions are the raw material for SHACL — the W3C standard for shapes a validator can actually run against real records. AOE derives them: cardinality becomes sh:minCount/maxCount, allValuesFrom becomes sh:class. Kinds with no faithful mapping are dropped, not guessed.

The line we won't cross

owl:minCardinality 1 licenses an inference: there is at least one, and if you can't see it you simply haven't been told. sh:minCount 1 is a verdict: an instance without one is invalid. Translating the first into the second manufactures a claim the source never made.

So every derived shape is sh:Warning, never sh:Violation, and carries provenance back to the row it came from. Promotion is a curator's recorded decision. The system may reorganize what it was told; it may never upgrade it into a stronger claim.

The most defensible slide in the deck for a semantics-literate audience — mechanically turning OWL cardinality into SHACL constraints is a common and genuinely wrong shortcut.

Shapes derived from LLM-extracted restrictions also carry the extraction confidence: "the manual says SHALL" is a model's reading of prose, not an axiom an author wrote. Shapes that arrived as SHACL keep their author's severity — they were published as validation and need no reinterpretation.

Same rule as the structural gate and the belief reviser, on a new surface. That consistency is the argument.

Two more capabilities, briefly

Many sources, one master — and facts, not just schema

Reconciling many sources

Organisations accumulate several ontologies of the same domain. Vector retrieval proposes candidate matches, an LLM adjudicates only the uncertain middle, and a classical-anchor ensemble refuses any LLM match without grounded lexical or structural support.

Merges that would violate a declared disjointness are automatically repaired — every removal reported.

Schema and instances

Beyond the schema, the same chunks yield individuals — "Acme Corp is a Company; Acme employs Bob."

Typing is schema-guided: an individual whose type isn't in the schema is dropped, not invented. Coreferent mentions are merged. Every fact carries the character span it came from.

Instances render on the canvas beside their classes — opt-in, one class at a time, because a schema has dozens of classes and an instance graph can have hundreds of thousands of nodes.

Compress this slide if you're running long — it's two capabilities that each deserve their own talk, and neither is the punchline.

Jargon note if it comes up: the schema half is conventionally called the T-box, the instance half the A-box. Nobody outside the field needs those words.

Part four

The result that changed how we spend effort

We were measuring something else when this turned up.

Slow down here. This act is the reason the talk is worth giving — everything before it is architecture, and architecture is cheap to claim.

Requirements-driven

An ontology exists to answer questions — so start there

A curator writes the competency questions the ontology must answer, or an LLM proposes candidates from the purpose statement and class labels. Every suggestion stays proposed until a human accepts it — nothing auto-persists — and a deterministic lint flags malformed questions before they waste anyone's time.

  • Accepted questions are formalized into queries and scored for coverage, producing a gap backlog and a release gate.
  • The set of terms those questions reference then scopes everything else: which cross-source matches matter, which instances are worth keeping.
  • The result is a use-case-shaped knowledge graph, not an everything-graph.

And running those questions as a benchmark is how we found the next slide.

The lint catches the four classic pitfalls: not phrased as a question, compound "and/or" clauses, yes/no binaries, and no domain term to ground against.

Set up the next slide explicitly: "we built the benchmark to measure coverage. What it actually taught us was something about names."

Measured — 71-question benchmark

Human curation is the highest-leverage input

Six curated label decisions, measured against a natural-language question benchmark. Identical across five runs.

We benchmarked the alternatives first — candidate ranking, join assembly, embedding-based concept resolution, clause pruning. Curation won.

So we built the product around that finding

If a handful of human decisions is worth more than another retrieval heuristic, then the job of the platform is to make those decisions cheap to make, and impossible to lose. That is exactly what the next two slides are.

Lead with the capability, not the post-mortem. The point of this slide is that we measured where effort pays — that's rigour, and it's why the curation workflow exists.

Say the base rate out loud: three-source questions are 8 of 71, so 15%→25% is two additional questions. The robust number is the overall 60→69% across all 71. An audience that spots the small sample before you name it stops trusting the deck — naming it first costs nothing and buys credibility.

The renames themselves: two classes each had an attribute labelled role. On Document it meant the kind of document; on Contact it meant the person's job. The right answer for the second was neither existing name — it was "job title", which no renaming rule would ever propose. That's the case for a human in the loop, in one example.

The curated lexicon

What a thing is called is a domain judgement

A machine detects the collision trivially — same label, two different concepts. It cannot resolve it, because the answer is frequently neither existing name.

Document.role ＋ Contact.role → collision queue → curator decides → "job title"
  • A decision, not an edit. Renaming one side only is often correct, so partial resolution is first-class. Re-deciding expires the prior decision rather than overwriting it — so "why is this called job title?" always has an answer with a name and a date on it.
  • Merged in at read time. Decisions overlay the extracted label everywhere one is shown or exported — entity lists, detail panels, the canvas, RDF export.
  • And it survives the next extraction. That guarantee is harder than it sounds — and it's the next slide.

The audit trail is genuinely half the value here. In a regulated environment, "who decided this and when" is the question that gets asked, and the string itself is the easy part.

Durability by design

A curated decision has to survive the next refresh

Every tool in this category re-runs extraction over changing sources — and the obvious way to build it loses the human's work.

The trap

Store the curated label on the concept. Refresh, and extraction reclaims the key curation had retired — resetting its expiry and reviving the old row.

You get two live rows for one attribute, and nothing reports an error. A "locked" flag doesn't save you: overwrite replaces the whole document, lock included.

What AOE does instead

Decisions live in their own store, outside the path extraction writes to, joined to concepts by identity and merged over the extracted label on read.

Survival becomes structural — it holds because of where the data lives, not because every future write path remembered a rule.

Proven, not asserted: an integration test against a live database confirms a decision survives repeated re-extraction — a guarantee no mock could establish.

Frame this as a capability slide, not a war story: the failure mode is generic to the category, and AOE is architected so it can't occur. The red card is the naïve implementation — say "the obvious way to build this," not "our bug."

If asked how we know: we argued it from reading the code, didn't trust that, and wrote the live-database test. It confirmed the analysis — one live row after a curator edit, two after a re-extraction on the naïve layout, and a decision in the current design surviving two consecutive re-extractions untouched.

This is a good differentiator question to put back to the room: ask your current tooling vendor what happens to a human correction on the next refresh. Most cannot answer it.

The principle

Ask any tool in this category one question

The question

What happens to the human's decision the next time the machine runs?

If the answer is vague

The human's work disappears on a refresh, the metric quietly regresses, and nobody is told. Every other guarantee in that product is decoration.

AOE's answer

It survives — structurally, and there's a test against a live database that says so. Same for every curation action: they all sit on a temporal layer where nothing is overwritten and everything is reversible.

This is the slide to leave up if you're asked to compare AOE to anything else. It's a question competitors mostly cannot answer, and it costs nothing to ask.

It generalises well beyond ontologies — any labelling tool, data-quality workflow, or human-in-the-loop annotation pipeline that also has an automated refresh has this exposure. Invite the room to go and ask it of their own stack.

Part five

Where it goes

Measuring the thing, then turning the dial.

Short landing. Two slides and the close.

Legibility

Because it's automated, it has to be measurable

Six signals, rolled into a 0–100 health score.

FaithfulnessDoes each class trace to real evidence? (LLM judge.)
Semantic validityAre the assertions internally coherent?
ConnectivityIs this a graph, or a bag of islands?
Structural integrityDo the relationships point at things that exist?
CompletenessHow much declared structure survived?
ConfidenceEvidence age and count, plus judge scores.

Not vanity numbers: connectivity and structural integrity are what the self-repair gate moves, and faithfulness is a hard cap no repair or revision may regress.

The link between this slide and the structural-gate slide is the point: the metric that proves the repair worked is the same metric that constrains what the repair is allowed to do.

Governance

Autonomy is a dial, not a default

When an engineer cuts a release candidate, a readiness review composes signals the system already computes — rule violations, the six metrics, the breaking-change report — and an LLM critic ranks findings as blocking, warning, or info.

AdvisoryThe report informs a human, who publishes. (Default.)
Gated-autonomousAuto-publish only with zero blocking findings and metrics clear of configured thresholds. Otherwise escalate.
Supervised-autonomousAuto-publish and notify, report attached for audit.

Two invariants that keep the higher settings honest

Faithfulness is a floor the review can never waive. And every release is reversible — which is only true because of the temporal model from part three.

Frame it as the same move that let CI/CD scale for code: human in the loop (a person must touch every item) becomes human on the loop (people set policy and handle exceptions).

Nobody starts on the third setting. The dial turns up as the signals earn it.

The bet

The future isn't a better one-shot extractor

It's a living system that proposes, grounds, versions and revises — with a human holding the pen.

Where we'd tell you to spend your effort

We benchmarked the algorithmic route against the human one, and human judgement won. The scarce resource in a system like this isn't model capability — it's expert judgement, and the engineering that decides whether that judgement is captured cheaply and then kept. That's what we built.

Close on the last sentence, not on a feature list. Then hand to the repo slide.

Likely questions: (1) how big can the graphs get — thousands of classes render fine, instances are opt-in per class; (2) which models — provider-configurable, the pipeline is model-agnostic; (3) what stops the LLM inventing classes — evidence constraints, multi-pass consistency, the judge, and a human gate.

Running it

Docker, Python 3.11+, Node 18+, and two API keys. make infra brings up the database — you never install one by hand, and make doctor preflights your keys, models and DB before you waste a run on a bad config.

Then open localhost:3000. It's a workspace, not a CLI.

Three things to try first

1. Point it at a database you already run — no LLM, no keys, nothing to hallucinate. A defensible first ontology in about a minute.

2. Upload two decks on one subject. Watch the second one revise rather than restart.

3. Rename a class, then re-extract — and watch the decision survive.

Issues and PRs welcome. The product requirements document is in the repo and is the real source of truth for what the system must do — which makes it an unusually easy codebase to propose against.
